# UI 读改存按钮的分区边界与零调用甄别

> **一句话**：UI 读改存按钮的分区边界与零调用甄别

## 现象

配���配置按 TabPage 分区后，「读取/修改/保存」三按钮的边界容易破：一是「读取」常被实现成全量重载（`LoadAlgorithmsConfig()` → `new` 配置对象 → **替换** Manager 持有的实例），导致其它 TabPage 已改未存的内存改动被整体丢弃；二是每页的「读取」会顺带回填别的 TabPage 的控件（两个回填方法被两页互用）。同时批量清理时，public 零调用方里既有真死成员，也有算法库的可复用工具与未启用通道的配套代码，前者误删会丢能力，后者误留会积灰。

## 根因

配置的所有权单元是 TabPage 时，UI 的每个读写动作都必须能被「它会动到哪些区」这个问题界定；而「读取」天然容易越界，因为它常被当作「刷新界面」而非「读回本区数据」。配置对象被替换与被就地更新是两种语义：前者丢弃未保存改动，后者保留——读取属于后者，保存才属于前者。零调用方则需要按「能力性质」而非「调用次数」判定去留。

## 判据

① UI 读改存三按钮必须建「按钮 → zone → 配置项」矩阵，逐按钮核对是否越界（严格边界：同页不同 TabPage 之间也算越界）；② 「读取」必须写回**现有**配置对象（⛔ 禁 `new` + 替换实例），并先 `Reload()` 载体再读（否则读到内存快照）；③ 跨区回填从按钮移除，被移走的控件交由页面构造时的批量回填负责；④ public 零调用方按四类甄别：未启用通道 / 预留 API（含算法库工具、配套通道）/ 接口覆写契约 / 真死——只删「空壳 + 零调用 + 无预留语义 + 非契约」者；⑤ 事件处理器即使空壳也**不能删**（Designer 反射订阅 ⇒ 删了编译不过）。

## 预防

- UI 读改存按钮的分区边界：读取只刷本 TabPage 的 zone 且写回现有对象不替换；零调用 public 按能力性质四分类，只删真死者
