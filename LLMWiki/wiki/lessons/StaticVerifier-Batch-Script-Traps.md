## 四之十四、⭐ 批量改文件的脚本级陷阱（六个：①~④ 2026-10-09 两次往返 `AdaWeldSystem_output` 回滚 · ⑤~⑥ 2026-10-16/19 实机发现 · ⑦~⑧ 2026-11-17 ADR 合并轮实证）

本轮改 3 个 Designer（`DataReviewerPage.Designer.cs` 删 5 个面板块、`MainPage.Designer.cs` 换容器），
脚本连崩 4 次，其中一次**已写盘才被断言拦下**，必须从 `AdaWeldSystem_output_<ts>.tar.gz` 回滚。

### ⛔ ① `io.open(encoding='utf-8-sig')` 会做 universal newline 转换（CRLF → LF）

**症状**：按 `\r\n` 构造的锚点**必然 0 命中**，而同一段代码用 `open(p,'rb').read()` 却能命中。
**根因**：`io.open(..., 'utf-8-sig')` 走文本模式，Python 做 newline 转换，`\r\n` 在**读进来时就没了**。
于是「按 `\r\n` 拼锚点 → 全文 search → 替换」三步全错，且**报错信息是 `count=0`，
看起来像锚点写错，实际是读取层已改内容**。

> ⛔ **判据**：批量改文件**一律按字节读**：`raw = open(p,'rb').read()`，
> 自己 `raw.split(b'\n')`（保住行尾里的 `\r`），改完 `b'\n'.join(lines)` 写回。
> **绝不用 `io.open(encoding=...)` 读进要按行尾做锚点的文件。**

这是本页「规则条目：锚点形态二分诊断」（原 rules/KR-024）的一个**新变体**：
那条讲「行内片段锚点不能带行尾」，这条讲「**读取层就会把行尾改掉**」。

### ⛔ ② `split(行尾)` 会把分隔符吃掉

`s.split('\r\n')` 得到的每段**都不含行尾**；把这些段当「行」插回去，CRLF 文件就变成 LF
（`loneLF` 恰好等于插入的段数）。
**正解**：按 `\n` 切（保住 `\r`），或**逐行显式补行尾**：

```python
new_rows = [ln.encode('utf-8') + (b'\r' if is_crlf else b'') for ln in new_lines]
```

**⚠️ 块切片变体（2026-10-16 实测）**：`ls..le` 切出的整块**末行自带 `\r`**，若用
`nl.join(new_lines)` 写回（`new_lines` 是**新行**、无 `\r`），块的**最后一行**就丢了 `\r`
⇒ 恰好 1 处孤 LF（`loneLF` 0→1）。**正解**：块替换输出按行显式补行尾，或切块时
`block = raw[ls:le]` 保留原尾 `\r` 且最后一行输出也带 `\r`；收尾断言 `loneLF 与改前基线一致`。

### ⛔ ③ 写盘必须在断言之后

上版顺序是 `write` → `assert crlf/loneLF`，断言**拦下了污染但文件已写坏**。
**正确顺序：算 → 断言 → 写**：

```python
out = b'\n'.join(lines)
if before_is_crlf and out.count(b'\n') - out.count(b'\r\n') != 0:
    raise SystemExit('abort before write')
open(p, 'wb').write(out)
```

**且要记住**：写盘前的 `sys.exit` 会让文件**保持原样**（看起来像"脚本没生效"）——
排查时先确认文件是否真的一致，别怀疑编码。

### ⛔ ④ `bytes` 字面量不能含中文

`b'... 原 TableLayoutPanel（4 列）...'` ⇒ `SyntaxError: bytes can only contain ASCII literal characters`。
注释段用 `str` 拼，最后统一 `.encode('utf-8')`；只有纯 ASCII 的属性行才用 bytes。

### ⚠️ 附带一条：判据自身也会「静默跳过」

首版校验器把 Span 的 11 项判据包在 `if m:`（`m` = Span 正则匹配结果）里，
**Span 缺失时其余项全被跳过** ⇒ 阴性对照出现「改前 48 项 / 改后 59 项」的**项数不一致**，
对照结论因此不可信。

> ⛔ **判据**：依赖前置匹配的判据组，**缺前置时要用占位值让下游自然 FAIL**，
> 绝不能 `if m:` 整块跳过。**两轮判据项数必须相等**，否则阴性对照无效。

### ⛔ ⑤ 重排类改动必须断言「视觉语义序」，集合相等掩盖不了顺序错乱（2026-10-16 业主实机发现）

四轮把 `gridAlgoControl` 54 控件按目标视觉序重排，校验器断言了「集合相等 / 54 格 / 6 标题 /
段成员全等」**全绿**，但业主实机看是「参数变少、倒灌进去」——**三处顺序错误全在语义层**：
① 段标题按语义编号**逆序**列出（视觉成了 ⑤→①）；② ⑤区两对参数误置于主标题与⑤标题之间
（跨段粘连）；③ 对内写成 `txt|lbl`（输入挤在标签前，左右列错位观感=参数丢失）。
集合与格数判据**对顺序完全失明**。

> ⛔ **判据（重排/合并类 UI 必加三条）**：
> 1. **段标题序 == 语义编号序**（按标题文本里的 ①②… 或已知标题列表断言出现顺序）；
> 2. **配对次序**（`lbl` 先于其 `txt/sel` 同行；输入只能在奇数列位）；
> 3. **跨段位置**（每个段成员必须落在其标题与下一段标题之间——`pos(member) > pos(title)`
>    且 `< pos(nextTitle)`）。
> 且必须**打印重建后的视觉结构逐行人工复核**（结构打印是抓这类错最快的手段，
> 2026-10-16 打印 19 行即一眼看出修复正确）。

### ⛔ ⑥ 删除/迁移 Designer 控件必须查「四形态」，少一形态就漏（2026-10-19 业主实机发现）

11 控件跨 Designer 迁移，脚本删了声明/属性块/挂载**三形态**，判据也只查这三种——业主实机
看到 SystemControlPage.Designer.cs 里 `this.selParamMono = new AntdUI.Select();` 还留着
（**CS0103 实锤**），且迁入侧**只删未迁**、`new` 行根本没搬过去（迁入侧运行时空引用）。

> ⛔ **判据（Designer 控件删除/迁移的四形态清单，逐形态断言 0 / 断言 1）**：
> 1. **实例化** `this.X = new T();` —— ⚠️ **不带点号**，`this\.X\.` 正则天然漏它；
> 2. **声明** `private T X;`
> 3. **属性块** `this.X.Prop = ...`（含跨行语句如 `Items.AddRange`）
> 4. **挂载** `Controls.Add(this.X);`
>
> 删除侧断言**全文 `\bX\b` 计数 = 0**（一网打尽，不逐形态枚举）；迁移侧断言
> **四形态各 = 1**。⚠️ 迁移≠删除+新增：**实例化在 ctor 顶部分区**，与属性块
> （InitializeComponent 中后段）位置相隔几百行，删除脚本极易只处理一处。

### 规则条目：批量改写先干跑校验全部锚点

- **规则要点（原 rules/KR-020）**：多文件多命中的批量改写**必须两阶段** —— 先跑干跑统计**每个**锚点在**每个**目标文件的命中数，任一为 0 即带完整计数报告**中止**；全命中才写盘。
- **判据**：⛔ 不用「脚本说替换成功」当判据；判据要求「与改动前完全一致」的计数须改为**同质性判据**（增删行必然改变行数 / 行尾计数）；锚点若只在兄弟替换之后才出现 ⇒ **顺序应用**（同一循环内校验 + 写盘），⛔ 不并行校验整组。
- **预防**：探针串要短、无 markdown 强调、**字节精确**（Designer 注释行可能带尾随空格）；整行替换要带上文件实测的终止符（见 lessons 的换行守恒条目）。

### 规则条目：锚点形态二分诊断

- **规则要点（原 rules/KR-024）**：**整行锚点带行尾，行内片段 / 行首前缀锚点不带行尾** —— 对片段锚点也追加行尾，锚点必然命中 0（要求锚点之后紧跟换行 ≡ 要求锚点恰为一整行）。
- **判据**：失败集与成功集**在形态上完全可二分** ⇒ **先自审判据**，⛔ 不怀疑内容写错或编码不一致（同一批里含 `—` / `～` / `⇒` 的整行锚点全部命中，足以排除编码假设）。
- **修法**：先试「带行尾」形式，命中数 ≠ 1 再回退「不带行尾」形式 `nl.join(old.split("\n"))`；`new` 用同一份文本即可（插入型替换在两种形式下都能正确落行）。

### ⛔ ⑦ 治理脚本写死绝对路径 ⇒ 「副本试跑」实际改了源目录（2026-11-17 ADR 合并轮实证）

- **现象**：为「先在副本目录试跑」写的一次性治理脚本，跑完副本后发现**源目录的 ADR 页被删了 6 页、51 个文件的引用被改写**。副本目录里的文件**一份没动**。
- **根因**：脚本顶部写死 `WIKI = r'D:\...\LLMWiki'`（绝对路径）⇒ 副本里执行的脚本仍然指向**源目录**；「跑在副本」只换了脚本文件的位置，**数据根没换**。
- **判据**：脚本里的路径常量是绝对路径 ⇒ **命中**；副本执行后「副本目录内容不变 + 源目录内容变化」⇒ **命中**（这是本坑的指纹）。
- **预防**：
  - 路径一律**从脚本位置推导**：`TOOLS_DIR = os.path.dirname(os.path.abspath(__file__))` → `WIKI = os.path.dirname(TOOLS_DIR)`；
  - 副本试跑**前后各取一次源目录 md5** 并断言相等 —— 副本试跑若动了源目录，必须立刻中止；
  - ⛔ 副本目录必须**先解锁只读属性再删**（`shutil.copytree` 会保留只读位，`rmtree(ignore_errors=True)` 静默失败 ⇒ 副本残留上轮状态 ⇒ 误判「本次改动无效」）。

### ⛔ ⑧ 治理脚本非幂等 ⇒ 二次执行累积污染（2026-11-17 ADR 合并轮实证）

- **现象**：合并脚本第二次执行后，ADR-Index 每行多一个 `|`（`|||`），承接页多出 2 个空行 —— 校验和与首次不一致。
- **根因**：三处「读进来 → 加一点 → 写回去」的字段在每次执行时都**追加**而非**替换**：
  ① 表格行拆分时把 `rest` 多存了一个 `|` 前缀 ⇒ 二次解析再拼一次；② 承接小节为空时仍插入空行块；
  ③ 表体段落替换时 `out` 以空行开头 ⇒ 二次执行 `start` 位置右移一位 ⇒ 前置多插空行。
- **判据**：同一脚本连续执行两次，两次之间**文件校验和必须完全一致** ⇒ 不一致即命中。⛔ 脚本自检时**必须包含幂等项**（只测「跑一次对不对」不够）。
- **预防**：所有「读改写」字段一律**先归一化再写入**（`rest` 用 `' | '` 连接并 strip 每一段）；插入前先判「目标小节是否已存在」；段落替换的 `out` **⛔ 不以空行开头**（否则段落起点漂移）。

## 五、成员遮蔽与回流

- **成员遮蔽（CS0108）**：派生类的 `Tag` / `_tag` / `StepXxx` 重复声明基类成员。
- **改名残留**：统一到基类 `Tag` 后 `_tag` 仍留着。
- **回流**：已禁用的调用点重新出现（如统一走 `DeviceLog` 后又新建类似封装）。
- **无用 using**：变更遗留。
- **csproj 路径完整性**：每条 `<Compile Include>` 都要在磁盘上解析到真实文件 —— 尤其**文件移动/改名之后**（2026-09-14 实测：文件在磁盘上，csproj 仍留旧路径，grep 文件名判据通过但**编译必失败**）。

## 七、.csproj 注册与路径存在性

> **规则要点（原 rules/KR-009）**：新建或移动 `.cs` 必须注册进 `.csproj`；**每条 `<Compile Include>` 都要在磁盘上解析到真实文件**。

- **现象**：文件在磁盘上、`.csproj` 仍留旧路径 ⇒ grep 文件名判据通过，但**编译必失败**（文件移动 / 改名后尤其高发）。
- **判据**：逐条 `<Compile Include="..." />` 做 `os.path.exists` 验证；⛔ 不用文件名 grep 判断。
- **预防**：移动 / 改名 / 合并目录时同步改写路径（路径变了注册即失效，与命名空间改不改无关）；操作步骤见 [[guides/Namespace-Compilation]] §1.1。

## 八、同文件禁止并发 Edit

> **规则要点（原 rules/KR-018）**：**同一个文件禁止并发两个 Edit** —— 两个调用都报「Successfully edited」，实际只落地一个。

- **现象**：两条 Edit 指向同一文件时**都报成功**，但只有一条真正写入（读-改-写竞态，后写者覆盖先写者）；曾整段丢失小节、表格与列表项。
- **判据**：同一文件的编辑**串行**（跨消息依次执行）；改完 grep 每条 `new_string` 的**特征子串**确认已落地 —— 「成功返回」**不等于**「改动已落盘」。
- **预防**：探针子串要短、无 markdown 强调（强调差异会造成假阴性）；竞态报 `EBUSY: resource busy or locked` 时串行重试即可（瞬时现象，非致命）；改完重跑扫描器，不假定先前绿灯仍成立。
