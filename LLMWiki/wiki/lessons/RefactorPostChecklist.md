# 大动作收归后的四项核查清单

> **一句话**：大动作收归后的四项核查清单

## 现象

把配置载体收归单一 Manager 后，遗漏集中在三处：① 子类 override 的基类属性在基类改造后成了死属性 —— 5 个 workflow 的 ConfigRelativeDir override 仍指向旧目录，使基类新默认值被 override 掉，结果 workflow 配置根本没走新 Manager、旧目录文件变孤儿（而「死属性」本身零引用，静态扫描查不出）；② 已删配置项的「只读忽略」读取分支残留（如 Adapt 区读 IS_COUNT_TYPE/COUNT_NUM 只为打一条 Info 日志），业主裁定完全舍弃旧配置后这类读取是纯噪音且让区域键清单与实际读写键数不一致；③ 零引用的孤儿配置文件与空目录不会自动消失 —— 收归后旧目录下的文件全仓零引用但仍留在磁盘，需逐个判定（注意扩展名可能是 .ilini 这类非 xml/ini）。

## 根因

收归类重构的完成判据不是「编译通过」而是「所有权唯一 + 旧路径零残留 + 配置项零遗漏」三件事同时成立；其中「子类 override 掉的基类属性」是最高频的漏点 —— 它让基类的新默认值失效，静态零引用扫描看不出（override 本身算一次引用），只有逐个 Manager 核对载体归属才能发现。而「只读忽略旧键」的残留分支会让配置项计数与区域键清单对不上，破坏「逐项可核」的基础；孤儿文件则要按全仓引用（排除路径迁移表）+ 扩展名白名单双口径判定。

## 判据

① 逐个 Manager 核对「正式载体」数（新建 INIFile/XdocumentReaderWriter 且路径非临时），须区分「正式载体」与「补键模板的临时载体」；② 核对「基类的可 override 属性」是否仍被子类 override（基类改了默认值但子类还指着旧值 ⇒ 改造失效）；③ 配置项完整性用「实际读写的键」与「声明的键清单」逐区双向 diff（两个方向都要查：实际有而未声明 / 声明有而不写）；④ 已删配置项的「只读忽略」分支一并物理删除；⑤ 孤儿文件判定用全仓引用（排除路径迁移表）+ 扩展名白名单（xml/ini 之外还有 .ilini 等）；⑥ 空目录一并清理。

## 预防

- 收归后核查四项：各 Manager 正式载体数（区分临时载体）、子类 override 的基类属性是否已失效、配置项双向 diff（实际 vs 声明）、已废旧键的只读忽略分支与孤儿文件一并物理清理
