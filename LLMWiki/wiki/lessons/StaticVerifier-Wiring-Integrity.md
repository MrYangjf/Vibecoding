## 三、接线完整性（绿灯但功能是哑的）

### 3.1 改签名必须审计每个调用点 —— 加可选参数只修编译，不修接线

加 `double p = 0.0` 让旧调用点**编译通过**，于是构建变绿而**功能是哑的**（新参恒为默认值，无任何报错）。

**两个高频漏点**：
| 漏点 | 后果 |
|---|---|
| **同文件内的调用点** | 改签名与改调用点常分两次编辑，忘第二次 |
| **Manager 门面层** | 底层加了参，上层 `UpdateRobotWeldParams` 不转发 ⇒ 外部值永远传不进来 |

**判据**：对本轮改过签名的每个方法，**跨文件**列出所有调用点，断言 `实参数 >= 必填参数数`；并**另设一条**断言新参**至少被赋过一次值**（grep 调用点，不能只确认方法存在）。

### 3.2 配置字段要「四点闭环」，不是「符号存在」

对每个配置属性，断言四条链都在：① INI/XML **键常量** ② **Load** 侧读回 ③ **Save** 侧写回 ④ 至少一个**消费者**（算法或 UI 绑定）。

只查「属性存在」会放过死字段。**实证漏网**：`CspMinSegMm` 有写回（`SaveProcessIni`）也有 UI 框，但**`LoadProcessIni` 里没有对应 `ReadDoubleIni`** ⇒ 用户改的值重启后静默回默认，**没有任何编译器或扫描器会抱怨**。

⚠️ **反向误报**：写侧可能用 `WriteInt`/`WriteBool` 而兄弟键用 `WriteString`。**按「键常量」匹配，不要按写入方法名硬编码**（否则报「缺失写回」的假阳性）。

### 3.3 成员存在性检查必须限定方法体

全文件正则会产生「成员缺失」假报。断言「某成员在某方法内被引用」时，先用花括号配平切出该方法体，只在体内搜。

### 3.4 ⭐ 多个前置条件不得合并进同一个提前返回 —— 处置方式不同就必须分治（2026-10-26 业主实机复查发现）

**事故**：`SystemControlPage.TimerRefresh_Tick` 初版写成

```csharp
private bool CanRefreshNow()   // ❌ 三个条件合并
{ return !IsDisposed && !Disposing && Visible && IsMotionReady(); }
...
if (!CanRefreshNow()) return;  // 一挡了之
```

两个前置条件的**应有处置不同**，合并后语义被抹平：

| 前置条件 | 不满足时应有的处置 |
|---|---|
| 设备已连接（`IsMotionReady()`） | **要回写 UI 控件**（开关自动回退 `Checked = false`）—— 否则控件显示「已开启」而实际不刷新 = 误导性 UI |
| 页面已切到（`Visible`） | **只跳过动作、保留控件状态** —— 用户回到本页时希望设置还在 |

业主原话已经区分了两种失效模式（「没有切换到对应页面**不需要去刷新 UI**」vs「没有连接上**自动退回**不刷新」），实现时却被合并 —— 于是「未连接」按「未切页」的方式处理，**只在代码里挡了刷新，界面上开关仍亮着**，业主断开控制器后一眼看出。

**判据（模式化，可静态查）**：门控函数若 `return` 多个条件，逐个问「这个条件不满足时，是否**需要回写任何状态**？」
- 有任一条件需要回写 ⇒ ⛔ 不得并入同一个 `bool` 判据，必须在调用处**分条处置**（本条每一支有自己的副作用）。
- 回写 UI 控件时**必须配抑制标志**：程序写 `Checked` 会触发 `CheckedChanged`（见 [[lessons/UiLayoutChangeSyncPitfalls]] 坑三），无抑制则每次回退/恢复都触发一轮处理器与日志。
- 状态回写要**幂等**：给「已回退」加标记位（本案例 `_refreshSuspendedByDisconnect`），否则 500ms 每拍重复回写与重复日志。

**判据（行为性，静态结构判据查不出 —— 必须补推演）**：本轮 `35/35` 里真正抓住缺陷的是**把 Tick 逻辑译成可执行模型跑场景**，而不是任何文本判据（文本判据在初版也是全绿的）。推演的固定场景集（门控类通用）：

```
① 开页即不满足前置 → 是否回退 + 是否仅一次日志
② 前置恢复 → 是否按裁定恢复（本案例：恢复默认 ON）
③ 再次不满足 → 是否再次回退（标记位是否被正确复位）
④ 前置不满足时用户手动操作控件 → 是否被拒绝并回退（否则控件会反复跳）
⑤ 已满足前置时用户主动关闭 → 是否被后台逻辑强拉回（这是「恢复默认」最常见的副作用）
⑥ 另一个前置不满足 → 是否只跳过且**保留**控件状态
```

> ⛔ **教训**：`4.x` 那批判据只证明「代码写得和我想的一样」，不证明「行为符合业主裁定」。凡改动涉及 状态回写 / 门控 / 自恢复，**必须补一份状态机推演**，并把场景集写进校验器。

### 3.5 CS0067 / CS0649 先取证再处置，符号名只信编译输出

**判据（归属）**：告警符号的类名 / 声明位置**必须从 `MSBuild` 输出逐字取**，⛔ 不得按「上一轮迁移过哪些成员」反推 —— 迁移后同名成员常分居两层，反推必然指错。

**判据（CS0067 事件从未被引用）**：
| 订阅侧 | 结论 | 处置 |
|---|---|---|
| 有订阅者（`+=`），但事件体**从不 `Invoke`** | 链路断在触发端 = **哑功能** | **补触发**（① 事件所需的输入从哪来 → ② 谁在何时下发 → ③ 触发点是否可达），⛔ 不得因「没人用」删订阅者 |
| 0 订阅 且 0 引用 | 死代码 | 删 |

**判据（CS0649 字段从未赋值）**：先列「声明 / 赋值 / 读取 / 消费者」四列；读取处只回传自身（如 `public X Foo => _foo;` 且 `Foo` 0 消费）= 死字段，删；有真实读取则补赋值，⛔ 不得反向删读取点。

**判据（补齐后）**：新增的输入（阈值 / 配置 / 开关）必须**同时**覆盖 ① 初始化下发 ② 运行期修改同步 —— 只做 ① 会让 UI 改完要重启才生效，且编译器不会报。

## 四、零消费不等于死成员

> **规则要点（原 rules/KR-011）**：审计报「0 消费者」时**不得直接下「死成员」结论**，先判定它是不是横切关注点的载体。

- **判据**：先问三件事 —— ① 它是不是日志标签 / 序列化键 / 权限标识 / 注册钩子等**横切关注点载体**；② `raw/` 原档是否把它列为**契约成员**；③ 可观测性 API（`StepStatusText` / `WorkElapsedMs`）与安全钩子（`CheckDeviceIOSafe`）**不因未使用而删除**。
- **处置**：提议「收紧类型 / 降低可见性」而非删除，由业主逐案裁决。
- **同族**：0 消费成员的业主裁定见 [[standards/CodeSimplification]] §一之二 顶层裁定 2。
