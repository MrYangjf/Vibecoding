## 九、本轮（2026-10-26 全库治理）新增判据与失效模式

> 本轮全库审计（12 项自建静态审计 + 项目自带 `scripts/csharp_review.py` 154 文件扫描）暴露的**校验器自身**问题。全部为**假阳性/假阴性**，不是代码缺陷。

### 9.1 工具的 stdout 编码会让整份扫描结果静默丢失（假阴性，最危险）

**症状**：`scripts/csharp_review.py` 对 `LineLaserWorkflow.cs` 直接抛 `UnicodeEncodeError: 'gbk' codec can't encode character '\u2212'` 并退出 —— 该文件**一条扫描项都没产出**，却因「异常退出」被上层当成「该文件无问题」。

**根因**：脚本 `print(json.dumps(..., ensure_ascii=False))` 走 **控制台代码页（GBK）**；`ensure_ascii=False` 保留了 U+2212（数学减号）等非 GBK 字符 ⇒ 打印阶段炸。

**修法（已落地）**：脚本 `main()` 入口统一
```python
for _stream in (sys.stdout, sys.stderr):
    if hasattr(_stream, 'reconfigure'):
        _stream.reconfigure(encoding='utf-8', errors='replace')
```
> ⛔ **判据层推广**：任何「批量扫描后统计命中数」的脚本，**打印阶段失败会让命中数静默归零**。上层统计必须能区分「扫描成功且 0 命中」与「扫描异常」，否则零命中恒等于健康。

### 9.2 「可空引用类型」判据须先分 class / struct

`ClassName?` 在 C# 8 才是可空引用类型；**`StructName?` 是 `Nullable<Struct>`，C# 7.3 合法**。实测 5 处 `MotorState? state = ...` 全部命中 `struct MotorState`（`MotionControl/WeldHeadSlaveDevice.cs:563`）⇒ **5 处误报**。
**判据**：报「可空引用类型」前，先用类型声明表把该名字映射到 `class` / `struct` / `interface` 再判。同源盲区见 [[lessons/StaticCheckSemanticBlindSpots]] §1。

### 9.3 「命名空间 ≠ 目录」判据须先读 ADR 的例外登记表

ADR-005 要求 `namespace = AdaWeldSystem + 目录路径`，但 **§3 例外二**明确 `ProductFileControl/{Abstractions,Records}` 为**扁平裁定**（子目录不产生子命名空间）。机械判据报 7 处偏离 ⇒ **全为误报**。
**判据**：规则型判据（命名空间对齐、region 命名、XML 覆盖率）**必须先读该 ADR 的「例外登记表」再落判据**，否则会把规则页当全集。

### 9.4 「UI 直控轴」判据须区分「轴实例成员」与「Manager 统一入口」

ADR-073 禁的是 UI 直调 `MontionAxis` 的 `AbsMove`/`JogMove`/`AxisStop`/`ServoOn*`/`HomeNoBlock`；`MontionManager.Instance.MoveTo/HomeAxis/ToggleServo/StopAxis/JogStart/StepMove` **正是该 ADR 规定的唯一出口**。机械判据若把这六个函数名一并列入禁集 ⇒ 14 处误报。
**判据**：禁集应按**接收者类型**限定（`axis.AbsMove(` 违规 / `manager.MoveTo(` 合规），不能只按方法名。

### 9.5 「新串计数 == 期望数」在多条表项产出同一新串时会误报

批量替换表里**两条不同的 old → 同一个 new**（例：两条不同的「前馈安全系数 + 单调方向锁（…演进）」注释归一到同一句）⇒ 该 new 在文件里出现 2 次，而「按单条表项期望值 1」判据报失败。**同理**：某 new 可能与文件中**既有**同形串重合（计数 2 而期望 1）。
**判据**：反向校验（reverse-apply）时，**只判「old 已不存在」与「new 存在」两个存在性事实，不判精确计数**；要判唯一性必须锚在**整行**或**带上下文的复合串**上（参见 [[lessons/JudgementDimensionGap]]「存在性 ≠ 唯一性」）。

### 9.6 行尾守恒断言须**按文件类型分式**（纯 LF / CRLF 两种口径）

批量删行时：
- **纯 LF 文件**：删 N 行 ⇒ `crlf` 恒 0、`loneLF` **减 N**；
- **CRLF 文件**：删 N 行 ⇒ `crlf` **减 N**、`loneLF` **不变**。

用同一套断言（`loneLF` 减 N）去校验 CRLF 文件 ⇒ **误判 ABORT**，改动被拦下不落盘（本轮实测命中 1 次）。断言须先按 `crlf > 0` 分流。

### 9.7 备份「按天去重」会让回滚点**不是本轮起点**（跨会话陷阱）

`tools/backup_adaweld.py` 按天去重：本轮 Step 2.1 命中「今日备份已存在」而**跳过**，于是拿到的 `AdaWeldSystem_backup_YYYYMMDD_HHMMSS.tar.gz` 可能是**更早会话**在同一天生成的，**早于该会话后续的改动**。实证：备份 10:24 生成，更早会话 11:07 才提交 ADR-075 §六 ⇒ 与备份比对时 **113 个文件出现差异**，其中 86 个是他人未提交工作。
**判据**：Step 2.1 跳过时**必须记录既有包的时间戳并与当前工作树比对**，否则「与备份 diff = 我的改动」这一前提不成立。**兜底**：用**反向应用表**（把本轮替换表 new→old 逐条回退）证明「当前文件 − 本轮表 = 本轮改前状态」，该判据不依赖备份新鲜度。

### 9.8 「代码骨架不变」是精简类改动的**最强**判据

本轮 27 个文件、180 处替换 + 2 行删除的**唯一**可靠证明是：**剥离注释与字符串字面量后，代码骨架与改前逐字节一致**（`strip_comments` + `strip_strings` + 逐行 diff）⇒ 零逻辑改动。
⛔ 注意：`strip_strings` 必须处理**转义引号**（`\"`），否则含转义的字符串行会误判为「代码变化」。

### 9.9 批量重排脚本的「移动」实现会因行号前移而变成「复制」

**症状**：写脚本按「成员顺序」自动重排 C# 类成员，26 个文件全部报告 `moved=12`（= 脚本轮次上限），且被改文件里**同一个声明出现了 12 份**。

**根因**：插入点用**删除前**的行号计算，而删除操作本身会让其后所有行号前移 ⇒ 插入点落到错误位置；下一轮重新解析时该声明仍在违规位置 ⇒ 反复搬同一块，最终变成复制。

**判据（关键）**：
- **先算插入点、再删**（或删后按「剩余行」重算插入点），二者不可混用；
- **每轮必须断言「该声明在文件内出现次数 == 1」**，否则立即中止；
- **落盘前做「成员集合零差异」校验**（类/方法/属性/字段名集合与改前完全相同）—— 这是「只改顺序、零增删」的机器可验证判据；
- **必须先做逐文件快照**（改前副本），异常时整目录回滚并逐字节复核；
- **轮次上限命中即视为失败**（`moved == 上限` 是脚本不收敛的信号，不是「修了很多」）。

### 9.10 判据的阈值与禁词必须逐条对齐标准原文

同一轮暴露两类口径失配：

- **阈值**：标准 §⑤「功能重叠合并」的判定原文是「**70% 以上**方法体相同」，脚本却用 `sim >= 0.5` ⇒ 把**语义不同**的重载（如 `CreateTable` 两版的列长与 `IsExistTable` 守卫不同）判成重复。**阈值必须取标准原文的数字**。
- **禁词**：为 M2 新增「region 名禁过程性命名」时写了裸词「临时」⇒ 误伤**领域名词**「**临时文件**」（`RecordFileStore.cs` 的「临时文件处理 / 临时文件列表」两个合规语义 region）。**禁词表须逐词核对是否可能出现在领域术语里**；宁可少禁词多靠人工判，也不误伤合规代码。

⇒ **通用规则**：扫描器判据的**阈值 / 禁词 / 例外**三项都必须能在标准原文里找到出处；找不到出处的判据不得上线。本轮先后踩中 **5 次**判据-标准失配（region 类型缺失、public 缺 XML、周期轮询 Sleep、薄包装、阈值），**全部当轮修正**。

### 9.11 「把声明搬到别处」的两步编辑极易变成「复制」—— 必须断言出现次数 == 1

**真实事故（2026-10-26）**：为修 §一① 成员顺序，把 `InterpolationMontionParam._axisCount` 从类中部**搬到类首**，分两步做：① 把新声明**插入**类首（旧的那份**没删**）；② 把构造函数搬到类尾。**第 ① 步的「插入」实为「复制」** ⇒ 同一字段声明两份 ⇒ 业主编译报 **CS0102「已包含 `_axisCount` 的定义」+「两个 `_axisCount` 之间具有二义性」**。

**教训**：
- **「移动」必须一次原子完成**（删旧 + 插新 一起做）；若必须分步，则**第二步必须断言旧文本已不存在**。
- 搬完立刻断言 **「该声明在文件内出现次数 == 1」**（`raw.count(decl) == 1`），不是「看起来对」。
- ⛔ **静态校验必须覆盖这一类**：原判据集**无「同类内成员重复定义」检查** ⇒ 只能靠编译器兜底。已补 `check_duplicate_members`（**ERROR 级**）：
  - 方法：**同名 + 同参数表** 重复 ⇒ CS0102；同名**不同参数表**是重载，**不报**；
  - 字段：**类体深度 1** 的严格声明（须带访问修饰符 / `const` / `static`）同名重复 ⇒ CS0102；方法内局部变量与 P/Invoke 属性实参**不计入**；
  - **互斥条件编译豁免**：两次声明之间存在 `#if` / `#else` 指令 ⇒ 位于互斥分支，**不是**重复（台达 Native 层的 `DllPath` 在 `#if X86` / `#else` 各声明一次，实际只编译一支）。
- **判据必做三重自证**（见 [[lessons/JudgementDimensionGap]]）：干净基线 0 error → **故意注入**该类错误必须被抓到 → 注入文件删除后再复跑。

### 9.12 判据把「同名不同义」当违规：`.Result` 的 9 处假阳性

**症状**：扫描器报「访问 Task.Result 阻塞，可能死锁」9 处，逐条看却全是 `e.Result` / `args.Result` —— **事件参数的属性**，同步取值，**根本不阻塞**。

**根因**：判据用 `\.Result\b` 这种**只看属性名**的模式，未区分「`Task.Result`（阻塞）」与「任意对象的 `.Result`（普通属性）」。

**修法**：收窄为「`Task`/`ValueTask` 的 `.Result`」与「`.GetAwaiter().GetResult()`」两种**真正阻塞**的写法。修后 9 处假阳性全部消失，warn 从 12 降到 2（剩 2 处是运控直线 `Thread.Sleep`，属时序红线，不改）。

⇒ **通用规则**：属性名类判据必须**带类型限定**（`Task.Result` vs `X.Result`），不能只看属性名 —— 与 §9.2「禁式判据先剥注释」、§9.4「禁集按接收者类型限定」同源。

### 9.13 批量插入文档注释必须**继承原块的缩进**

**症状**：批量补 `<param>`/`<returns>` 后，插入的 `///` 行**顶格**（无缩进），与同一 doc 块内原有行不齐 —— 视觉上像坏掉的注释块。

**修法**：(1) 插入时**继承 doc 块首行的前导空白**；(2) 事后用「同一连续 `///` 段内缩进必须一致」的规范化脚本扫一遍兜底（本轮修正 111 个文件）。

⇒ **行级插入类批改一律要求「插入行缩进 = 参照行缩进」**。

### 9.14 成员顺序的自动化重排：文本块整体搬运 + 三重自证

**背景**：§一①「成员顺序」违规 133 处 / 72 文件，人工逐个改不可行。

**可行实现（已跑通，修 45 处）**：
- **整块切分**：以扫描器解析出的成员 span 切块，**块内含 `///` 文档 + `[特性]` 行 + 声明 + 尾部空行**；块间残留内容并入前块 ⇒ 切分**无缝**；
- **字节级重组自证**：`header + 按原序拼接的所有块 == 原类体区间`（不等则放弃该文件）⇒ 证明**切分无损**；
- **区域感知**：`#region`/`#endregion` 把块切段，**段内重排、段间不跨越**（跨区移动会破坏区域结构）；
- **oracle + 回滚**：重排后扫描器违规数须下降，否则不写；写前逐文件快照，异常整目录回滚。

**踩过的三个坑（各自都导致过「复制而非移动」或误判）**：
1. **插入点用删除前的行号** ⇒ 删除后行号前移 ⇒ 同一声明被复制多份（曾致 12 份）⇒ 改为**删除后重新解析**再定位；
2. **用 `Method.end_line` 定位方法块尾** ⇒ 该值**不含方法闭合大括号** ⇒ 闭合行落进缺口 ⇒ 改用「从 `start_line` 起做花括号/`;` 配对」；
3. **表达式体成员（`=> x;`）无 `{`** ⇒ 大括号配对找错位置 ⇒ 统一用语句配对法。

⇒ **通用规则**：批量重排类改码必须「**先证明切分无损，再证明搬后有序，最后证明违规数下降**」三关全过才落盘；任何一关不过就**放弃该文件**而非硬改。

### 9.15 工具固化：5 个固定脚本 + 新增禁区 #9/#10

**2026-10-26 收口**：把批改经验固化为 `scripts/simplify_*.py` 五个固定脚本（详见 [[standards/CodeSimplification-Tooling]]），**后续批改只调参数、不重写逻辑**：

| 脚本 | 作用 | 关键内建约束 |
|---|---|---|
| `simplify_guard.py` | 结构守卫 | brace / XML 标签 / 成员集合 / 行尾+BOM / 缩进同质；**任一 FAIL 立即回滚** |
| `simplify_apply_member_order.py` | 成员顺序重排 | 字节级重组自证 + 区域感知 + oracle + 快照回滚 + **嵌套类型护栏** |
| `simplify_apply_docs.py` | 注释补全/压缩 | **private `///` 保留**；插入行继承缩进；多行 summary 可压 |
| `simplify_selfcheck.py` | 口径-判据一致性 + 三重自证 | 干净基线 → 注入必被抓 → 零变化 |
| `simplify_run.py` | 一键巡检 | guard + 扫描器聚合 + selfcheck |

**新增禁区**：

| # | 坑 | 症状 | 对策 |
|---|---|---|---|
| 9 | **块内含嵌套类型声明** | 嵌套类被字段解析器收进来 ⇒ 搬动它等于把整个嵌套类体当成员移动 ⇒ 解析器失控（实测**单文件 250s CPU、零产出**） | 护栏：块内含 `class/struct/interface/enum` 声明 ⇒ **该类不搬动**，记 `nested-type` 跳过 |
| 10 | **输出被缓冲，用户看不到进度** | 脚本跑 1~2 分钟但终端零回显 ⇒ 被误判为「卡死」并被取消 | ① 管道**禁用** `Select-Object -Last`（必须消费完整流才输出）② **按目录分批**（每批 5~20s）③ 长任务用**后台 + 重定向日志 + 轮询**（日志实时增长 = 进度可见） |

⇒ **通用规则**：批改类脚本**必须自带进度输出**（逐文件一行），并在被人使用时**分批**；「无回显的长任务」与「空转」在用户侧不可区分，等同于故障。

### 9.16 批改脚本「复制而非移动」会把文件**撕裂**——brace 计数查不出来

**症状（2026-10-26 业主报「打开项目发现很多结构上 {} #region 错位产生的 BUG」）**：3 个文件出现**孤立语句**与**大括号错位**，编译报 CS0102：

- `EthernetXmlComm.cs`：类内出现孤立语句 `TcpClient.Send(message.GetBytes("utf-8"));`、孤立 `{`、孤立 `Log("客户端已连接");`；`Dispose()` / `Disconnect()` 各出现两份（一份 `override` 一份非 `override`）
- `WeldHeadSlaveDevice.cs`：字段 `MotorPulsePerMm` 声明两份
- `IntelligentLaserCam.cs`：类内孤立 `MessageLevel.Warning);` + `return false;`

**根因**：批改脚本的插入点用**删除前的行号**计算 ⇒ 位置算错 ⇒ 成员被**切开**搬走，碎片留在原地。

**⛔ 为什么我的校验全部「绿灯」**（这是最值得记的一条）：

| 校验项 | 为什么漏 |
|---|---|
| 花括号平衡（`{` 数 == `}` 数） | 碎片里恰好有**等量**的 `{` 与 `}` ⇒ **总数抵消** |
| 成员集合比对（`set`） | **重复成员不改变集合** ⇒ CS0102 不可见 |
| region 配对数 | 撕裂不改变 `#region`/`#endregion` 计数 |
| 行尾守恒 | 撕裂保持行数 ⇒ 计数守恒 |

⇒ **判据必须升级**：
1. **成员用多重集（Counter）不用集合（set）** —— 重复/丢失都能抓；
2. **加「语句级合法性」检查**：类体（depth==1）内出现**非声明形态的完整语句**（以 `;` 结尾且不以声明/控制关键字开头）⇒ 孤立语句 ⇒ 撕裂；
3. **加「当前文件独有的非注释行」比对**（与改前基线做行集合差）—— 最准的碎片定位手段；
4. **行尾同质检查必须无条件执行**（不能只在有 baseline 时做）：批量插入注释若用 LF 插进 CRLF 文件 ⇒ 混合行尾 ⇒ IDE 解析/折叠异常（本轮 72 文件命中，1,043 行 loneLF）。

**修复路径**（无 git 时）：从**改动前**的备份恢复受损文件（先验证「成员数量一致」⇒ 恢复不丢成员，只丢注释类改动，可重跑脚本补回）→ 重跑注释补全 → 统一行尾 → 复验。

⇒ **通用规则**：**brace 平衡 + 成员集合 = 弱判据**，不足以证明批改安全；批改类改码的放行条件至少要「**成员多重集零差异 + 无孤立语句 + 无重复成员 + 行尾同质 + region 归属不变**」五项全过。

### 9.17 ⭐ 批改放行必须真编译：本机 MSBuild 可用，「无编译器」前提已失效（2026-10-26 复检）

**背景**：同日 16:37 的「结构守卫 PASS + 扫描器 ERRORS=0」交付后，业主报「多处编译报错」。本轮改用 Visual Studio 18 Insiders 的 MSBuild 真编译，一次性列出 **18 个文件 / 124 条错误**：全部是类闭合花括号被提前（成员被挤到类外）、`try` 体被搬出方法、整段方法体丢失。结构守卫全绿的原因很直接——它只比对 **brace 总数与成员多重集**，而 `}` 只是**换了位置**，总数仍然平衡、成员数量也未变。

**本机可用的编译入口（已实测）**：
- `C:\Program Files\Microsoft Visual Studio\18\Insiders\MSBuild\Current\Bin\MSBuild.exe`（或同目录 `amd64\MSBuild.exe`）
- `MSBuild.exe AdaWeldSystem\AdaWeldSystem.csproj /t:Rebuild /p:Configuration=Debug /p:Platform=AnyCPU /v:m /nologo /clp:ErrorsOnly`
- 前提：`C:\Program Files (x86)\Reference Assemblies\Microsoft\Framework\.NETFramework\v4.8` 已存在（本机已确认）
- 通过判据：**退出码 0 且 `bin\Debug\AdaWeldSystem.exe` 时间戳刷新**；警告可接受，错误必须为 0。

**规则**：
1. 任何批量压缩 / 重排 / 删段类改码，收尾必须跑一次 `/t:Rebuild` 真编译，不得以静态守卫 PASS 代替。
2. 花括号平衡、成员多重集、region 配对只覆盖「数量」，覆盖不了「位置」；**位置错误只有编译器能定案**。
3. 无 git 时以同日**改码前的 backup 包**为参照：逐文件比对「当前独有的非注释行」可定位被搬走的片段；结构大面积错乱的文件直接按备份对应区段做**字节级替换**（保留 BOM 与行尾），再重编译。

### 9.18 ⭐ 成员顺序重排的根因：最后一块把 `#endregion` + `}` 一起搬走（2026-10-26 实证）

**症状**：18 文件 / 124 条编译错误；类闭合 `}` 出现在方法之前，成员被挤到 namespace 作用域。
**根因**：旧实现 `blocks[i] = lines[span_i.start : next.start]`，最后一块的终点用了 `cls_end`（类闭合行）⇒ `#endregion` 与 `}` 被当成「最后一个成员的一部分」；当该成员在段内被排到前面时，`}` 随之提前，类提前闭合。
**修复**：改为「**成员块 + 固定间隙**」模型——成员块只含自身行，`#region/#endregion/}`/空行作为 gap 原地不动；重组后用结构守卫断言 namespace 作用域不得出现成员/裸块。
**判据**：`simplify_guard.py` 新增 `structural_fails()`（namespace 级结构）与 `region_fails()`；`simplify_run.py` 增加真 MSBuild 编译门禁。**花括号平衡与成员多重集都查不出此类位置错误，必须真编译**。
**口径**：成员顺序判定改为「每个 `#region` 段内；跨 region 不比较」（业主 2026-10-26 裁定），旧「类内全局顺序」废止。

### 9.19 ⭐ 成员顺序判据的三个假阳性源（2026-10-29 清零后复盘）

1. **嵌套类型成员**：`parse_file` 原先 `pos = end_pos + 1` 跳过嵌套类，外层类把嵌套类方法当成自身成员 ⇒ 外层出现「方法排在字段后」假违规。修复：`pos = m.end()` 收录嵌套类型，外层按 `start_line/end_line` 区间排除嵌套成员。
2. **析构函数**：`~ClassName()` 被 `CTOR_RE` 当成 `#ctor`，出现「构造函数排在 public 方法后」假违规。修复：名字前一个字符为 `~` 时跳过，不参与成员顺序。
3. **方法内局部变量**：`for (int i = 0; ...)` 被 `FIELD_RE` 当成字段（如 `NavPage.F.i`）。修复：字段只认**类体深度 0**（`scan_text` 从类体 `{` 之后开始，成员深度 0、方法体内 ≥1）。

**规则**：成员顺序判据的输入必须是「外层类自身的成员」；凡命中嵌套类型 / 析构函数 / 方法内局部变量，先自审判据，不要改代码。
